# Requirements Document

## Introduction

PUCT Book Builder is an offline opening-book generation system for dlshogi (dlcobra), targeted at the World Computer Shogi Championship (WCSC).

The system grows an opening-book graph by running PUCT (Polynomial Upper Confidence for Trees) search from a configured root position. Unlike the current `MAKE_BOOK` implementation in `usi/main.cpp`, which holds the whole book in an in-memory `std::map<Key, std::vector<BookEntry>>` and rebuilds it from trial descents, PUCT Book Builder keeps every node and edge in a disk-resident PostgreSQL database. Disk capacity, not RAM, becomes the limit on book size. PostgreSQL is the only supported database; no second storage backend is in scope.

The target book size is 100,000,000 book nodes. At roughly 80 legal moves per position that scale rules out any storage layout whose per-move records must be retrieved individually, so this document states node-and-edges retrieval as a single operation and leaves the physical grouping of a node's edges to the design.

One book graph in one PostgreSQL database holds the whole book: one search run, one propagation pass, and one export carrying the best moves of Black-to-move and White-to-move positions alike. The search is colour-blind, as Requirement 4 criterion 12 states, so two per-colour runs would have produced two statistically independent samples of the same random process at roughly 267 GB each rather than two different books, whereas one graph searched with the same total effort gives twice the visits per book node and correspondingly more reliable negamax values. Colour-symmetric search is also what value accuracy requires: under negamax a Black-to-move node's value is one minus the minimum over White's replies, so getting one side's move right depends on accurate values at the other side's nodes.

One export file likewise serves both sides. The engine's `Book::probeConsideringDrawDepth` performs a negamax over the book file at game time through `Book::getMinMaxBookScore`, recursing through opponent replies, so a file holding only one side's positions would return no entry at every opponent node and that recursion would terminate immediately; a file containing both sides gives that probe mode positions to recurse through.

When the search expands a position that has not been visited before, the system looks the position up in an imported YaneuraOu Terashock book (テラショック定跡) and injects that book's candidate moves and evaluations as additional children and priors. This keeps the generated book aware of the move choices a Terashock-based opponent is likely to play, so the resulting book competes with those lines instead of leaving them unexplored.

A search run has no budget. It keeps descending until the operator stops it; nothing in the configuration bounds the number of descents or the wall-clock duration of a run.

After growing the graph, the system runs a negamax value propagation pass over the book graph (the "Terashock-ization" step) to determine a best move and a propagated value for every position, then exports the result in Apery binary format for the dlshogi USI engine and in YaneuraOu `.db` text format for interoperability. That propagation is visit-aware: because a minimum over child values gives a barely searched leaf the same authority as a heavily searched subtree, an edge whose visit count falls below a configured threshold contributes its own accumulated mean value instead of the negamax value of the subtree below it, so a single noisy neural-network evaluation cannot dominate a whole line.

Out of scope: game-time book consumption. The USI engine reads the exported Apery book file during a game and never connects to the database, so no live database probing during play is required of this system.

## Glossary

- **PUCT_Book_Builder**: The complete system described by this document, comprising the components below.
- **Board_State**: A Shogi position consisting of piece placement, both players' hands, and the side to move. Ply count is not part of a Board_State.
- **Position_Key**: A fixed-width identifier of at least 128 bits derived from a Board_State, used as the primary identity of a Book_Node.
- **Position_Key_Function**: The component that computes a Position_Key from a Board_State.
- **Book_Node**: A persisted record representing one Board_State, holding the Position_Key, the SFEN string, the visit count, the accumulated value sum, the terminal state, the propagated value, and the propagated best move.
- **Book_Edge**: A persisted record representing one legal move from a parent Book_Node, holding the parent Position_Key, the child Position_Key, the move in USI notation, the prior probability, the visit count, the accumulated value sum, the Terashock evaluation value, and the Terashock search depth. The accumulated value sum of a Book_Edge is expressed from the perspective of the side to move at that Book_Edge's parent Book_Node, as required by Requirement 4 criterion 4.
- **Book_Graph**: The directed graph formed by all Book_Node and Book_Edge records held in one PostgreSQL database. Transpositions cause the Book_Graph to be a directed graph rather than a tree.
- **Node_Store**: The component that persists and retrieves Book_Node and Book_Edge records in a PostgreSQL database.
- **Cache_Budget**: A configuration value, in bytes, bounding the resident memory that Node_Store may use for caching Book_Node and Book_Edge records.
- **Search_Coordinator**: The component that performs PUCT selection, expansion, and value backup over the Book_Graph.
- **Search_Worker**: One concurrent execution unit of the Search_Coordinator.
- **Selection_Descent**: One traversal from the root Book_Node down to a Book_Node that is expanded or is terminal.
- **In_Flight_Set**: The set of Position_Keys that Search_Workers are currently expanding or evaluating.
- **Evaluator**: The component that produces a policy distribution over legal moves and a win rate for a Board_State using the dlshogi neural network.
- **Terashock_Book**: An opening book in YaneuraOu `.db` text format, produced by the Terashock or Super Terashock generation method, supplied as input to PUCT_Book_Builder.
- **Book_DB_Parser**: The component that parses YaneuraOu `.db` text into Terashock_Entry records.
- **Book_DB_Printer**: The component that formats Terashock_Entry records back into YaneuraOu `.db` text.
- **Terashock_Entry**: One parsed position from a Terashock_Book, holding the SFEN string and an ordered list of Terashock_Move records.
- **Terashock_Move**: One candidate move of a Terashock_Entry, holding the move in USI notation, the expected opponent reply in USI notation or the literal `none`, the evaluation value, the search depth, and the selection count.
- **Terashock_Index**: The lookup structure that maps a Position_Key to the Terashock_Entry of the corresponding Board_State.
- **Prior_Mixer**: The component that combines the Evaluator policy distribution with Terashock-derived move weights into Book_Edge prior probabilities.
- **Repetition_Resolver**: The component that classifies the result of a move as draw by repetition, win by perpetual check, loss by perpetual check, or non-repetition, using the move path of the current Selection_Descent.
- **Cyclic_Flag**: A boolean marker on a Book_Node value indicating that the value was derived through a path involving repetition and is therefore path-dependent.
- **Value_Propagator**: The component that computes a propagated value and a propagated best move for every Book_Node by negamax propagation over the Book_Graph.
- **Propagation_Pass**: One execution of the Value_Propagator over the Book_Graph, begun by the propagate command of Requirement 9 criterion 1 and ended by the completion reported under Requirement 9 criterion 7. The most recently completed Propagation_Pass is the propagation pass whose completion Requirement 12 criterion 8 refers to. A Book_Node's propagated value is current where the Value_Propagator computed and stored that propagated value during the most recently completed Propagation_Pass, and is stale where the Value_Propagator computed and stored that propagated value during an earlier Propagation_Pass.
- **Child_Contribution**: The win rate that one Book_Edge contributes to the negamax minimum taken at its parent Book_Node during value propagation, expressed from the perspective of the side to move at that Book_Edge's child Board_State, determined by Requirement 9 criterion 15.
- **Propagation_Visit_Threshold**: A configuration value, an integer, being the Book_Edge visit count below which the Value_Propagator takes that Book_Edge's Child_Contribution from the Book_Edge's own mean value instead of recursing into the Book_Edge's child Book_Node. Propagation_Visit_Threshold is an absolute visit count applied during propagation and is distinct from Export_Visit_Threshold, which is a visit-count ratio applied at export time by Requirement 12 criterion 5.
- **Book_Exporter**: The component that writes the Book_Graph to an Apery-format binary book file and to a YaneuraOu `.db` text book file.
- **Apery_Book_File**: A binary book file consisting of `BookEntry` records as defined in `cppshogi/book.hpp`, sorted ascending by key.
- **Operator**: The person who configures and runs PUCT_Book_Builder.
- **Progress_Reporter**: The component that emits run statistics to the log destination.

The configuration values referenced throughout this document, together with their permitted ranges, are enumerated in Requirement 13 criterion 7.

## Requirements

### Requirement 1: Disk-Resident Node Storage

**User Story:** As an engine developer, I want the book search tree stored in a database on disk, so that the book can grow beyond the size of available RAM.

#### Acceptance Criteria

1. THE Node_Store SHALL persist each Book_Node as a record uniquely identified by its Position_Key, retaining exactly one record per distinct Position_Key and storing the SFEN string of up to 128 characters, the visit count as a non-negative integer of at least 0 and up to at least 4,294,967,295, the accumulated value sum in the closed interval from -4,294,967,295 to 4,294,967,295, the terminal state, the propagated value in the closed interval from 0 to 1, and the propagated best move in USI notation of up to 7 characters.
2. THE Node_Store SHALL persist the Book_Edges of every Book_Node such that each Book_Edge is identified by the pair of its parent Position_Key and its move in USI notation, retaining exactly one Book_Edge per such pair, where that identity is logical and holds for every physical grouping of a Book_Node's Book_Edges within the storage layout.
3. WHEN the Search_Coordinator requests a Book_Node by Position_Key, THE Node_Store SHALL return, in a single operation, the Book_Node record together with every Book_Edge record whose parent Position_Key equals that Position_Key, for counts of 0 to at least 600 Book_Edge records, ordered ascending by move in USI notation.
4. IF no Book_Node record exists for a requested Position_Key, THEN THE Node_Store SHALL return a node-absent result that is distinguishable both from a Book_Node record having zero Book_Edge records and from an operation failure, and SHALL create no Book_Node record for that Position_Key.
5. WHILE a search run is in progress, THE Node_Store SHALL serve read and write operations for a Book_Graph containing at least 100,000,000 Book_Node records while keeping the resident memory it uses for caching Book_Node and Book_Edge records at or below Cache_Budget.
6. WHEN the Node_Store writes a Book_Node record and its Book_Edge records for one expansion, THE Node_Store SHALL apply the write as a single atomic unit, so that any concurrent or subsequent read returns either all records of that expansion or none of them.
7. FOR ALL Book_Node records written and then read back without intervening writes, THE Node_Store SHALL return integer, string, and terminal-state field values exactly equal to the written values and real-valued field values equal to the written values within a relative tolerance of 0.000000001 (round-trip property).
8. IF a read or write operation requires cache capacity that would exceed Cache_Budget, THEN THE Node_Store SHALL evict previously cached Book_Node and Book_Edge records and SHALL complete the operation rather than failing it.
9. IF a write of a Book_Node record and its Book_Edge records for one expansion fails, THEN THE Node_Store SHALL leave the Book_Graph content equal to its state immediately before the write, SHALL retain no record from the failed write, and SHALL return a write-failure result identifying the Position_Key of the expansion.

### Requirement 2: PostgreSQL Storage and Schema Management

**User Story:** As an engine developer, I want the book stored in one PostgreSQL database whose schema the builder manages itself, so that a competition run starts from an empty database without manual setup.

#### Acceptance Criteria

1. THE Node_Store SHALL persist every Book_Node and Book_Edge in the PostgreSQL database named by the configured PostgreSQL connection settings and SHALL satisfy every criterion of Requirement 1.
2. IF a connection attempt to the configured PostgreSQL database does not succeed within 5 seconds, THEN THE Node_Store SHALL retry the connection up to Connection_Retry_Limit additional attempts, applying that same 5-second limit to each attempt, waiting 1 second before the first retry and doubling the wait before each subsequent retry up to a maximum wait of 60 seconds per retry.
3. IF the number of consecutive failed connection attempts reaches Connection_Retry_Limit plus one, THEN THE Node_Store SHALL report a connection failure to the Operator identifying the configured PostgreSQL host, port, and database name and the number of attempts made, and SHALL exit leaving the persisted Book_Graph containing every expansion write that completed before the first of those failed attempts and containing no record of any expansion write that did not complete.
4. WHEN PUCT_Book_Builder starts and the configured PostgreSQL database contains no PUCT_Book_Builder schema, THE Node_Store SHALL create the schema, including the indexes required by Requirement 1 criterion 3, SHALL record in that schema the schema version identifier of the running PUCT_Book_Builder, and SHALL complete both the creation and that recording before accepting any command from the Operator.
5. IF the configured PostgreSQL database contains a PUCT_Book_Builder schema whose recorded schema version identifier equals the schema version identifier of the running PUCT_Book_Builder and in which one or more schema elements or indexes required by Requirement 1 criteria 1 to 3 are absent, THEN THE Node_Store SHALL create only the absent elements, SHALL leave every already present schema element and index unaltered, and SHALL leave every existing Book_Node and Book_Edge record unchanged.
6. IF schema creation fails or does not complete within 300 seconds, THEN THE Node_Store SHALL report a schema-creation failure to the Operator identifying the configured PostgreSQL host, port, and database name and indicating whether the cause was a failure or the 300-second limit, SHALL leave no partially created schema element in the database, and SHALL exit without writing any Book_Node or Book_Edge record.
7. WHEN the Node_Store creates the PUCT_Book_Builder schema, THE Node_Store SHALL record the configured Root_Position in that schema as the Root_Position of the Book_Graph and SHALL return that recorded Root_Position unchanged on every subsequent start over that Book_Graph.
8. IF PUCT_Book_Builder starts and the configured PostgreSQL database contains a PUCT_Book_Builder schema whose recorded schema version identifier is absent or differs from the schema version identifier of the running PUCT_Book_Builder, THEN THE Node_Store SHALL report a schema-version-mismatch error to the Operator stating the recorded identifier or its absence and the identifier of the running PUCT_Book_Builder, SHALL create and alter no schema element, and SHALL exit without reading or writing any Book_Node or Book_Edge record.
9. IF the connection to the configured PostgreSQL database is lost while a search run is in progress, THEN THE Node_Store SHALL suspend every read and write operation, SHALL treat every Book_Node and Book_Edge write that was in progress as a failed write as defined by Requirement 1 criterion 9, SHALL attempt to re-establish the connection using the per-attempt limit, retry count, and wait schedule of criterion 2, and SHALL resume the suspended read and write operations if the connection is re-established within those attempts.

### Requirement 3: Position Identity and Transposition Merging

**User Story:** As an engine developer, I want positions reached by different move orders to share one node, so that search effort and evaluations are not duplicated across the book.

#### Acceptance Criteria

1. THE Position_Key_Function SHALL produce a Position_Key of the same fixed width of at least 128 bits for every Board_State.
2. FOR ALL pairs of Board_States with identical piece placement, identical hands, and identical side to move, THE Position_Key_Function SHALL produce equal Position_Keys, including when the two Board_States were reached by different move sequences, at different ply counts, or in different Selection_Descents.
3. FOR ALL pairs of distinct Board_States taken from a verification sample of at least 1,000,000 distinct Board_States that differ in piece placement, hands, or side to move, THE Position_Key_Function SHALL produce zero pairs of equal Position_Keys (collision-free property over the verification sample).
4. THE Position_Key_Function SHALL produce the same Position_Key for the same Board_State across separate invocations, separate Search_Workers, and separate PUCT_Book_Builder runs.
5. WHEN the Search_Coordinator expands a move whose resulting Board_State already has a Book_Node record, THE Search_Coordinator SHALL set the child Position_Key of the new Book_Edge to the Position_Key of that existing Book_Node record, SHALL NOT create a second Book_Node record for that Position_Key, and SHALL leave that existing Book_Node record's visit count, accumulated value sum, terminal state, propagated value, and propagated best move unchanged.
6. IF the Search_Coordinator reads a Book_Node record whose Position_Key equals the Position_Key of the Board_State being expanded but whose stored SFEN string denotes a different piece placement, hands, or side to move, THEN THE Search_Coordinator SHALL NOT create a Book_Edge referencing that Book_Node record, SHALL leave that Book_Node record's fields unchanged, and SHALL report a Position_Key collision, identifying both SFEN strings, to the Progress_Reporter.
7. FOR ALL Book_Edge records, including those created by transposition merging under criterion 5, the child Position_Key SHALL equal the Position_Key of the Board_State reached by applying the recorded move to the parent Book_Node Board_State (consistency invariant).

### Requirement 4: PUCT Selection and Expansion

**User Story:** As an engine developer, I want the book to be grown by PUCT search, so that search effort concentrates on lines that matter for competitive play.

#### Acceptance Criteria

1. WHEN a Selection_Descent starts, THE Search_Coordinator SHALL begin at the Book_Node whose Position_Key equals the Position_Key of the configured Root_Position Board_State and SHALL set the descent depth of that Book_Node to 0.
2. WHILE the current Book_Node is not terminal and has at least one Book_Edge record that is not excluded by criterion 7, THE Search_Coordinator SHALL advance to the child Book_Node of the Book_Edge that maximizes the PUCT score equal to the Book_Edge's mean value plus the configured exploration constant, in the closed interval 0.1 to 5.0, multiplied by the Book_Edge's prior probability multiplied by the square root of the parent Book_Node's visit count divided by one plus the Book_Edge's visit count, using the value 0.5 as the mean value of a Book_Edge whose visit count is 0 and that has no recorded Terashock-derived mean value, and SHALL select the Book_Edge whose move in USI notation is lexicographically smallest when two or more Book_Edges attain PUCT scores equal within a tolerance of 0.000001.
3. WHEN a Selection_Descent reaches a Book_Node that has no Book_Edge records, is not terminal, and whose Board_State has between 1 and 600 legal moves, THE Search_Coordinator SHALL expand that Book_Node by creating exactly one Book_Edge for every legal move of its Board_State, each with visit count 0 and accumulated value sum 0.
4. WHEN a Selection_Descent completes, THE Search_Coordinator SHALL increment by exactly 1 the visit count of every Book_Node and every Book_Edge on the descent path, SHALL add to the accumulated value sum of every Book_Node on the descent path the descent value expressed from the perspective of the side to move at that Book_Node, and SHALL add to the accumulated value sum of every Book_Edge on the descent path the descent value expressed from the perspective of the side to move at that Book_Edge's parent Book_Node, being the same perspective as that parent Book_Node's own accumulated value sum, where the descent value expressed from the perspective of a given side to move lies in the closed interval 0 to 1 and equals the leaf descent value where that given side to move equals the side to move at the leaf Board_State and equals one minus the leaf descent value where that given side to move differs from the side to move at the leaf Board_State.
5. FOR ALL Book_Nodes, the visit count SHALL equal the sum of the visit counts of that Book_Node's Book_Edge records plus one (visit-count invariant for nodes reached by a single parent path).
6. WHERE the configured Max_Book_Ply is an integer in the closed interval 1 to 1024, THE Search_Coordinator SHALL end a Selection_Descent at the Book_Node reached after exactly Max_Book_Ply moves from the Root_Position, SHALL create no Book_Edge records for that Book_Node, and SHALL assign the descent value for that Book_Node from its Evaluator win rate or, if the Book_Node is terminal, from its terminal state.
7. IF a Selection_Descent reaches a Book_Node whose Position_Key is in the In_Flight_Set, THEN THE Search_Coordinator SHALL exclude the Book_Edge leading to that Book_Node from selection for the remainder of that Selection_Descent and SHALL resume selection at the parent Book_Node over the remaining Book_Edges.
8. IF no Book_Node record exists for the configured Root_Position when a Selection_Descent starts, THEN THE Search_Coordinator SHALL create the Book_Node for the Root_Position Board_State with visit count 0 and accumulated value sum 0 before beginning that Selection_Descent.
9. IF every Book_Edge of the current Book_Node is excluded from selection by criterion 7, THEN THE Search_Coordinator SHALL abandon that Selection_Descent without changing any Book_Node or Book_Edge visit count or accumulated value sum, SHALL report the abandoned Selection_Descent to the Progress_Reporter, and SHALL start the next Selection_Descent within 100 milliseconds.
10. WHILE a search run is in progress, THE PUCT_Book_Builder SHALL apply every Book_Node write and every Book_Edge write of that run to exactly one Book_Graph, being the Book_Graph held in the PostgreSQL database named by the configured PostgreSQL connection settings, and SHALL write no record to any other Book_Graph.
11. WHEN the Search_Coordinator expands a Book_Node during a Selection_Descent as defined in criterion 3, THE Search_Coordinator SHALL treat that Book_Node as the leaf of that Selection_Descent and SHALL end that Selection_Descent at that Book_Node with the value backup of criterion 4.
12. FOR ALL Selection_Descents over a Book_Graph holding given Book_Node and Book_Edge field values and given Evaluator results, THE Search_Coordinator SHALL determine the Book_Edge selected by criterion 2 and the expansion performed by criterion 3 independently of the side to move at every Book_Node on the descent path, so that the sequence of Position_Keys visited and the set of Book_Edge records created are the same whichever side is to move at each visited Book_Node (colour-independence property).
13. WHILE no stop request from the Operator is pending, THE Search_Coordinator SHALL start a further Selection_Descent whenever a Search_Worker is available, without any bound on the total number of Selection_Descents of a search run, on the wall-clock duration of a search run, or on the number of Evaluator invocations applied to one Book_Node, and SHALL end the search run only on a stop request as defined in Requirement 10 criteria 5 through 7.

### Requirement 5: Neural Network Evaluation of Expanded Nodes

**User Story:** As an engine developer, I want new positions evaluated by the dlshogi network, so that priors and values reflect the strength of the trained model.

#### Acceptance Criteria

1. WHEN the Search_Coordinator expands a Book_Node whose Board_State has at least one legal move, THE Evaluator SHALL produce exactly one win rate for the Board_State, expressed from the perspective of the side to move, and exactly one probability for each legal move of the Board_State, and SHALL produce no probability for any move that is not a legal move of that Board_State.
2. WHEN the number of pending Board_States reaches the configured Batch_Size, THE Evaluator SHALL invoke the neural network with exactly Batch_Size pending Board_States.
3. WHILE the number of pending Board_States is greater than zero and below Batch_Size, WHEN the configured Batch_Timeout has elapsed since the earliest pending Board_State was accumulated, THE Evaluator SHALL invoke the neural network with all pending Board_States.
4. FOR ALL Evaluator outputs, each probability SHALL lie in the closed interval from 0 to 1 and the sum of the probabilities over the legal moves SHALL equal 1 within a tolerance of 0.001 (normalization invariant).
5. FOR ALL Evaluator outputs, the win rate SHALL lie in the closed interval from 0 to 1, where 0 denotes a certain loss and 1 a certain win for the side to move.
6. IF a neural network invocation returns an error, returns results for fewer Board_States than the invoked batch contains, or returns a win rate or a move probability that is not a finite number, THEN THE Evaluator SHALL report the invocation as failed for every affected Board_State, and THE Search_Coordinator SHALL remove each affected Board_State's Position_Key from the In_Flight_Set, SHALL leave the corresponding Book_Nodes unexpanded with no Book_Node field changed and no Book_Edge record created, and SHALL report the failure and the number of affected Board_States to the Progress_Reporter.
7. IF the sum of the neural network policy outputs over the legal moves of a Board_State is 0 or is not a finite number, THEN THE Evaluator SHALL assign every legal move of that Board_State a probability equal to 1 divided by the number of legal moves and SHALL report the substitution to the Progress_Reporter.

### Requirement 6: YaneuraOu Book Format Parsing and Printing

**User Story:** As an engine developer, I want to read and write YaneuraOu `.db` book files, so that Terashock books can be imported and generated books can be shared.

#### Acceptance Criteria

1. WHEN the Book_DB_Parser reads a line beginning with `sfen ` whose remainder contains at least one non-whitespace character and at most 256 characters after leading and trailing whitespace are removed, THE Book_DB_Parser SHALL start a new Terashock_Entry whose SFEN string is that trimmed remainder and whose Terashock_Move list is empty.
2. WHEN the Book_DB_Parser reads a candidate-move line, defined as a line that follows the `sfen ` line of the current Terashock_Entry, does not begin with `#` or `sfen `, and contains exactly five whitespace-separated fields, THE Book_DB_Parser SHALL append to the current Terashock_Entry a Terashock_Move built from the fields in the order move, opponent reply, evaluation value, search depth, selection count, preserving the order in which the candidate-move lines appear, where the move field is 1 to 7 non-whitespace characters, the evaluation value is an integer in the closed interval from -32000 to 32000, the search depth is an integer in the closed interval from 0 to 127, and the selection count is an integer in the closed interval from 0 to 4294967295.
3. WHEN the Book_DB_Parser reads a candidate-move line whose opponent reply field is exactly the literal `none`, THE Book_DB_Parser SHALL record the opponent reply of the Terashock_Move as absent and SHALL record the remaining four fields as defined in criterion 2.
4. WHEN the Book_DB_Parser reads a line beginning with `#`, THE Book_DB_Parser SHALL treat the line as a comment, SHALL exclude it from every Terashock_Entry, and SHALL continue parsing the following line.
5. IF the Book_DB_Parser reads a line that matches none of the recognized line forms of criteria 1 through 4 and 10 through 12, including a line beginning with `sfen ` whose trimmed remainder is empty or longer than 256 characters, a non-comment line whose field count is other than five, and a candidate-move line whose evaluation value, search depth, or selection count field is not an integer within the bounds of criterion 2, THEN THE Book_DB_Parser SHALL report the line number and the line content to the Progress_Reporter, SHALL discard that line without adding a Terashock_Entry or a Terashock_Move, SHALL retain every Terashock_Entry and Terashock_Move parsed before that line, and SHALL continue parsing the following line.
6. WHEN the Book_DB_Printer is invoked with a Terashock_Entry list of 0 to 1000000 records, THE Book_DB_Printer SHALL write as the first output line the header line `#YANEURAOU-DB2016 1.00` and as the second output line a `# NOE:<count>` line whose `<count>` is the decimal number of Terashock_Entry records in the list, writing `# NOE:0` for an empty list.
7. WHEN the Book_DB_Printer is invoked with a Terashock_Entry list, THE Book_DB_Printer SHALL write each Terashock_Entry, in the order of the list, as a line consisting of `sfen ` followed by the Terashock_Entry SFEN string, followed by one line per Terashock_Move in the list order and in the field order defined in criterion 2, separating adjacent fields with a single space character and writing the literal `none` for an absent opponent reply.
8. FOR ALL Terashock_Entry lists of 0 to 1000000 records, parsing the output of the Book_DB_Printer SHALL produce a Terashock_Entry list equal to the input list, where equality means the same number of records in the same order, equal SFEN strings, equal Terashock_Move counts per record, and equal move, opponent reply, evaluation value, search depth, and selection count for each Terashock_Move at the same list index (round-trip property).
9. FOR ALL well-formed YaneuraOu `.db` texts containing 0 to 1000000 `sfen ` lines and containing no line that criterion 5 would reject, printing the result of parsing SHALL produce a text that parses to a Terashock_Entry list equal, under the equality definition of criterion 8, to the Terashock_Entry list produced by parsing the original text (round-trip property).
10. WHEN the Book_DB_Parser reads a line beginning with `#` that matches the pattern `#YANEURAOU-DB2016 <version>` where `<version>` is 1 to 16 non-whitespace characters, THE Book_DB_Parser SHALL record `<version>` as the header version string, replacing any previously recorded header version string.
11. IF the Book_DB_Parser reads a candidate-move line before any line beginning with `sfen ` has been read, THEN THE Book_DB_Parser SHALL report the line number and the line content to the Progress_Reporter, SHALL discard that line without creating a Terashock_Entry, and SHALL continue parsing the following line.
12. WHEN the Book_DB_Parser reads a line that contains no non-whitespace characters, THE Book_DB_Parser SHALL discard the line without reporting to the Progress_Reporter, SHALL leave the current Terashock_Entry unchanged, and SHALL continue parsing the following line.

### Requirement 7: Terashock Knowledge Injection at Node Expansion

**User Story:** As an engine developer, I want Terashock book moves injected when a new position is expanded, so that the generated book covers and contests the lines a Terashock-based opponent will play.

#### Acceptance Criteria

1. WHERE a Terashock_Book path is configured, WHEN PUCT_Book_Builder starts, THE Terashock_Index SHALL map the Position_Key computed by the Position_Key_Function from the SFEN string of every Terashock_Entry parsed from that Terashock_Book to that Terashock_Entry, SHALL retain the last parsed Terashock_Entry and report a duplicate-SFEN count to the Progress_Reporter when two Terashock_Entry records yield equal Position_Keys, and SHALL return the Terashock_Entry for a given Position_Key within 1 millisecond at the 95th percentile for a Terashock_Book of at least 10,000,000 Terashock_Entry records.
2. WHEN the Search_Coordinator expands a Book_Node whose Position_Key has a Terashock_Entry, THE Search_Coordinator SHALL record, on each Book_Edge whose move in USI notation equals the move in USI notation of a Terashock_Move of that Terashock_Entry, the evaluation value and the search depth of that Terashock_Move, and SHALL record the Terashock evaluation value and the Terashock search depth as absent on every other Book_Edge of that Book_Node.
3. WHEN the Search_Coordinator expands a Book_Node whose Position_Key has a Terashock_Entry, THE Prior_Mixer SHALL set each Book_Edge prior probability to the sum of the Evaluator probability for that move multiplied by one minus the configured Terashock_Prior_Weight and the Terashock-derived weight for that move multiplied by the configured Terashock_Prior_Weight, where the Terashock-derived weight is 0 for every Book_Edge whose Terashock evaluation value is absent, and the Terashock-derived weights over the Book_Edges of that Book_Node sum to 1 within a tolerance of 0.001.
4. IF the move in USI notation of a Terashock_Move is not a legal move of the expanded Book_Node's Board_State, THEN THE Search_Coordinator SHALL discard that Terashock_Move, SHALL exclude it from the Terashock-derived weights of criterion 3, SHALL increment the illegal-Terashock-move counter reported by the Progress_Reporter, and SHALL complete the expansion using the remaining Terashock_Moves of that Terashock_Entry.
5. WHERE the expanded Book_Node has a Terashock_Entry and a Book_Edge has a recorded Terashock evaluation value, THE Search_Coordinator SHALL initialize that Book_Edge's mean value to the win rate obtained from the recorded Terashock evaluation value using the configured Eval_Coef, expressed from the perspective of the side to move at the expanded Book_Node, and clamped to the closed interval from 0 to 1.
6. FOR ALL expanded Book_Nodes, the set of Book_Edge moves SHALL equal the set of legal moves of the Board_State, and no Book_Edge SHALL exist for a move that appears only as a Terashock_Move (legality invariant, independent of Terashock injection).
7. WHERE Terashock_Prior_Weight is 0, THE Prior_Mixer SHALL set each Book_Edge prior probability equal to the Evaluator probability for that move within a tolerance of 0.001.
8. IF the configured Terashock_Book path cannot be read or its parsing yields zero Terashock_Entry records, THEN THE PUCT_Book_Builder SHALL report an error to the Operator indicating that the configured Terashock_Book is unreadable or contains no Terashock_Entry records and SHALL exit before writing to the Node_Store.
9. IF the expanded Book_Node's Position_Key has no Terashock_Entry, THEN THE Prior_Mixer SHALL set each Book_Edge prior probability equal to the Evaluator probability for that move within a tolerance of 0.001 and THE Search_Coordinator SHALL record the Terashock evaluation value and the Terashock search depth of every Book_Edge of that Book_Node as absent.
10. FOR ALL expanded Book_Nodes, each Book_Edge prior probability SHALL lie in the closed interval from 0 to 1 and the sum of the Book_Edge prior probabilities of that Book_Node SHALL equal 1 within a tolerance of 0.001 (prior normalization invariant).

### Requirement 8: Repetition and Terminal State Handling

**User Story:** As an engine developer, I want repetitions, mates, and declaration wins scored correctly, so that the competition book does not steer into a lost or drawn result.

#### Acceptance Criteria

1. WHEN a move leads to a Board_State whose occurrence count, counting the occurrence produced by that move among the Board_States on the current Selection_Descent path starting at the Root_Position, reaches four, and neither side delivered check at all four of those occurrences, THE Repetition_Resolver SHALL classify the move as draw by repetition.
2. WHEN the Repetition_Resolver classifies a move as draw by repetition, THE Search_Coordinator SHALL assign as the descent value the configured Draw_Value_Black if the side to move at the repeated Board_State is Black and the configured Draw_Value_White if that side is White, where both configuration values are win rates for the side to move in the closed interval from 0 to 1.
3. WHEN a move leads to a repetition of four occurrences in which the moving side delivered check at all four occurrences and the opposing side did not deliver check at all four occurrences, THE Repetition_Resolver SHALL classify the move as loss for the moving side and THE Search_Coordinator SHALL assign a descent value of 0 expressed as the win rate of the moving side.
4. WHEN a move leads to a repetition of four occurrences in which the opposing side delivered check at all four occurrences and the moving side did not deliver check at all four occurrences, THE Repetition_Resolver SHALL classify the move as win for the moving side and THE Search_Coordinator SHALL assign a descent value of 1 expressed as the win rate of the moving side.
5. WHEN the Search_Coordinator reaches a Board_State with zero legal moves, THE Search_Coordinator SHALL mark the Book_Node terminal state as loss for the side to move and SHALL assign a descent value of 0 expressed as the win rate of the side to move.
6. WHEN the Search_Coordinator reaches a Board_State in which the side to move satisfies every WCSC declaration-win condition, namely that its king stands within the opponent's three ranks, that it is not in check, that at least 10 of its pieces other than its king stand within the opponent's three ranks, and that its declaration point total, counting each rook and each bishop whether promoted or not as 5 points and every other piece other than the king as 1 point, is at least 28 points for Black and at least 27 points for White, THE Search_Coordinator SHALL mark the Book_Node terminal state as win for the side to move and SHALL assign a descent value of 1 expressed as the win rate of the side to move.
7. WHEN the Search_Coordinator assigns a descent value that was derived from a repetition classification, THE Search_Coordinator SHALL set the Cyclic_Flag on the Book_Node of the repeated Board_State, on the leaf Book_Node of the Selection_Descent, and on every Book_Node between them on the descent path, and SHALL leave the Cyclic_Flag unset when the descent value was derived from a terminal state other than repetition.
8. WHILE a Book_Node has the Cyclic_Flag set, THE Value_Propagator SHALL recompute that Book_Node's value from the propagated values of its child Book_Nodes on the current propagation path rather than reusing the stored propagated value.
9. IF a move leads to a repetition of four occurrences in which both the moving side and the opposing side delivered check at all four occurrences, THEN THE Repetition_Resolver SHALL classify the move as draw by repetition and THE Search_Coordinator SHALL assign the descent value defined in criterion 2.
10. WHEN a move leads to a Board_State whose occurrence count on the current Selection_Descent path starting at the Root_Position is fewer than four, THE Repetition_Resolver SHALL classify the move as non-repetition and THE Search_Coordinator SHALL leave the descent value to be supplied by the Evaluator win rate or by a terminal state classification.
11. WHEN the Search_Coordinator marks a Book_Node terminal state as win or loss, THE Search_Coordinator SHALL create no Book_Edge record for that Book_Node and SHALL end the Selection_Descent at that Book_Node.

### Requirement 9: Negamax Value Propagation

**User Story:** As an engine developer, I want leaf evaluations propagated to the root by negamax, so that each book position records the best move under the assumption that both sides play the book's best line.

#### Acceptance Criteria

1. WHEN the Operator invokes the propagate command, THE Value_Propagator SHALL compute, for every Book_Node reachable from the configured Root_Position by following Book_Edge records from parent Position_Key to child Position_Key, exactly one propagated value expressed as a win rate in the closed interval from 0 to 1 from the perspective of that Book_Node's side to move, and exactly one propagated best move or the absence of a propagated best move.
2. FOR ALL Book_Nodes whose terminal state is unset and that have at least one Book_Edge record, the propagated value SHALL equal 1 minus the minimum of the Child_Contributions of all of that Book_Node's Book_Edge records, where the Child_Contribution of each Book_Edge is the value determined by criterion 15 (negamax invariant, where the negation of a win rate v is 1 minus v).
3. FOR ALL Book_Nodes whose terminal state is unset and that have at least one Book_Edge record, the propagated best move SHALL be the move of a Book_Edge whose Child_Contribution is within 0.000001 of the minimum used in criterion 2, and WHERE more than one Book_Edge satisfies that condition, the propagated best move SHALL be the one that sorts first in ascending USI notation order.
4. WHEN the Value_Propagator reaches a Book_Node whose terminal state is set, THE Value_Propagator SHALL set the propagated value to 1 for a terminal state of win for the side to move and to 0 for a terminal state of loss for the side to move, SHALL record the propagated best move as absent, and SHALL NOT derive that Book_Node's propagated value from its Book_Edge records.
5. WHEN the Value_Propagator encounters a Book_Node that is already on the current propagation path, THE Value_Propagator SHALL treat the revisit as a draw by repetition, SHALL use Draw_Value_Black for a Black side to move and Draw_Value_White for a White side to move as the Child_Contribution of the Book_Edge leading to that revisit, and SHALL NOT store that value as the revisited Book_Node's propagated value.
6. WHILE the propagation pass runs, THE Value_Propagator SHALL keep its resident memory at or below Cache_Budget.
7. WHEN the propagation pass completes, THE Value_Propagator SHALL report to the Progress_Reporter the number of Book_Nodes processed, the number of draw-by-repetition revisits resolved under criterion 5, the unevaluated-leaf count from criterion 10, and the propagated value of the Root_Position.
8. FOR ALL Book_Graphs, running the propagation pass twice without intervening search SHALL produce, for every Book_Node, a propagated value equal within 0.000001 to and a propagated best move identical to the propagated value and propagated best move produced by running it once (idempotence property).
9. WHEN the Value_Propagator reaches a Book_Node whose terminal state is unset, that has no Book_Edge records, and that has an Evaluator win rate, THE Value_Propagator SHALL set the propagated value to that Evaluator win rate and SHALL record the propagated best move as absent.
10. IF the Value_Propagator reaches a Book_Node whose terminal state is unset, that has no Book_Edge records, and that has no Evaluator win rate, THEN THE Value_Propagator SHALL set the propagated value from Draw_Value_Black for a Black side to move and from Draw_Value_White for a White side to move, SHALL record the propagated best move as absent, and SHALL increment the unevaluated-leaf count reported by the Progress_Reporter.
11. IF the Operator invokes the propagate command while the Node_Store contains no Book_Node record for the Root_Position, THEN THE Value_Propagator SHALL report an error indicating the absent Root_Position to the Operator and SHALL exit without modifying any Book_Node record or Book_Edge record.
12. WHERE the configured Propagation_Visit_Threshold is greater than 0, WHEN the Value_Propagator determines the Child_Contribution of a Book_Edge whose visit count is greater than 0 and below Propagation_Visit_Threshold, THE Value_Propagator SHALL NOT recurse into that Book_Edge's child Book_Node, SHALL set that Child_Contribution to 1 minus that Book_Edge's mean value, being the Book_Edge's accumulated value sum divided by the Book_Edge's visit count expressed from the perspective of the side to move at the parent Book_Node and clamped to the closed interval from 0 to 1 before that subtraction, and SHALL store that Child_Contribution as the propagated value of no Book_Node.
13. WHERE the configured Propagation_Visit_Threshold is greater than 0, WHEN the Value_Propagator determines the Child_Contribution of a Book_Edge whose visit count is 0, THE Value_Propagator SHALL NOT recurse into that Book_Edge's child Book_Node, SHALL set that Child_Contribution to the Evaluator win rate of the Book_Node record whose Position_Key equals that Book_Edge's child Position_Key where such a Book_Node record exists and holds an Evaluator win rate, SHALL set that Child_Contribution to Draw_Value_Black where no such Evaluator win rate is available and the side to move at that Book_Edge's child Board_State is Black and to Draw_Value_White where no such Evaluator win rate is available and that side to move is White, and SHALL store that Child_Contribution as the propagated value of no Book_Node.
14. WHERE the configured Propagation_Visit_Threshold is 0, THE Value_Propagator SHALL determine the Child_Contribution of every Book_Edge without applying criterion 12 or criterion 13, so that the Child_Contribution of every Book_Edge whose child Book_Node has an unset terminal state and is not already on the current propagation path equals the propagated value of that child Book_Node (pure negamax over every Book_Edge).
15. THE Value_Propagator SHALL determine the Child_Contribution of a Book_Edge by applying the first applicable rule of the following ordered list: the terminal rule of criterion 4 where the child Book_Node's terminal state is set; the on-path revisit rule of criterion 5 where the child Book_Node is already on the current propagation path; the below-threshold rules of criteria 12 and 13 where the Book_Edge's visit count is below the configured Propagation_Visit_Threshold; and otherwise the propagated value of the child Book_Node as computed by criteria 2, 9, and 10.
16. THE Value_Propagator SHALL derive every Child_Contribution determined under criterion 12 or criterion 13 from the stored Book_Edge visit count, the stored Book_Edge accumulated value sum, the stored Evaluator win rate of the child Book_Node, Draw_Value_Black, Draw_Value_White, and Propagation_Visit_Threshold alone, and SHALL leave each of those stored values unchanged by the propagation pass, so that criterion 8 holds for every Book_Graph containing Book_Edges resolved under criteria 12 and 13.

### Requirement 10: Resumability and Crash Recovery

**User Story:** As an engine developer, I want a long book run to resume after interruption, so that months of GPU time are not lost to a restart.

#### Acceptance Criteria

1. WHEN PUCT_Book_Builder starts and the Node_Store contains at least one Book_Node record, THE Search_Coordinator SHALL begin its first Selection_Descent at the Book_Node of the configured Root_Position over the persisted Book_Graph, SHALL treat a Book_Node that has at least one Book_Edge record or a non-empty terminal state as already holding Evaluator results, and SHALL NOT invoke the Evaluator for such a Book_Node.
2. WHEN PUCT_Book_Builder starts and before the first Selection_Descent begins, THE Search_Coordinator SHALL clear every entry of the In_Flight_Set without reading the Book_Node records those entries identify, SHALL leave the visit count and accumulated value sum of every persisted Book_Node and Book_Edge unchanged by the clearing, and SHALL report the number of cleared entries to the Progress_Reporter.
3. IF PUCT_Book_Builder terminates while an expansion write is in progress, THEN on the next start THE Node_Store SHALL present for that Position_Key either the Book_Node record together with one Book_Edge record for every legal move of its Board_State, or no Book_Node record and no Book_Edge record for that Position_Key.
4. FOR ALL Book_Nodes, applying the same expansion result twice SHALL leave the Book_Node and Book_Edge records equal to the state after applying it once (idempotence property).
5. WHEN the Operator sends a stop request, THE Search_Coordinator SHALL complete the Selection_Descents in progress, SHALL flush pending writes to the Node_Store, and SHALL exit within 60 seconds of receiving the request with an indication to the Operator that the stop completed.
6. WHILE a stop request is pending, THE Search_Coordinator SHALL start no further Selection_Descent and SHALL invoke the Evaluator for no further Board_State.
7. IF the Selection_Descents in progress and the pending Node_Store writes are not both complete within 60 seconds of the stop request, THEN THE Search_Coordinator SHALL discard every expansion write that is not complete, SHALL report a forced-shutdown indication to the Operator, and SHALL exit while leaving the persisted Book_Graph satisfying criterion 3.
8. IF PUCT_Book_Builder starts and the Node_Store contains Book_Node records but contains no Book_Node record whose Position_Key equals the Position_Key of the configured Root_Position, THEN THE PUCT_Book_Builder SHALL report a root-mismatch error naming the configured Root_Position to the Operator and SHALL exit before writing any record to the Node_Store.

### Requirement 11: Concurrent Search Workers

**User Story:** As an engine developer, I want multiple workers expanding the book at once, so that the GPU and the database are both kept busy.

#### Acceptance Criteria

1. WHILE the configured Worker_Count is within its permitted range, THE Search_Coordinator SHALL run exactly Worker_Count Search_Workers concurrently, each performing Selection_Descents independently over one shared Book_Graph served by one Node_Store instance.
2. WHEN a Search_Worker begins expanding a Book_Node, THE Search_Coordinator SHALL add that Book_Node's Position_Key to the In_Flight_Set as a single atomic test-and-add that succeeds for exactly one Search_Worker, and SHALL complete that add before the Evaluator is invoked for that Board_State.
3. WHEN a Search_Worker's expansion attempt for a Book_Node ends, whether by a committed expansion write, by an Evaluator failure, by abandonment of the expansion, or by termination of that Search_Worker, THE Search_Coordinator SHALL remove that Book_Node's Position_Key from the In_Flight_Set within 1000 milliseconds of that outcome, and SHALL also remove any Position_Key that has remained in the In_Flight_Set for more than 300 seconds without its expansion being committed.
4. WHILE a Position_Key is in the In_Flight_Set, THE Search_Coordinator SHALL apply the configured Virtual_Loss as an additional visit count and an equal number of losing value contributions to every Book_Edge whose child Position_Key equals that Position_Key when computing that Book_Edge's PUCT score, SHALL apply it identically while a stop request is pending and while an Evaluator failure is being handled, and SHALL exclude the Virtual_Loss contribution from the Book_Edge visit count and accumulated value sum persisted by the Node_Store.
5. FOR ALL sets of expansions whose expanded Book_Nodes have pairwise distinct Position_Keys (independent expansions), the resulting Book_Node and Book_Edge field values SHALL be equal for every order in which the expansions are applied (confluence property).
6. IF two Search_Workers attempt to create a Book_Node record with the same Position_Key, THEN THE Node_Store SHALL retain exactly one Book_Node record, being the first record committed, SHALL leave that record's evaluation fields unchanged by the later attempt, SHALL return a duplicate-detected result to the later Search_Worker so that it continues with the retained Book_Node, and SHALL report the duplicate count to the Progress_Reporter without terminating either Search_Worker.
7. IF a Search_Worker's atomic add to the In_Flight_Set fails because the Position_Key is already present, THEN THE Search_Coordinator SHALL leave that Book_Node unexpanded, SHALL NOT invoke the Evaluator for that Board_State, and SHALL continue that Selection_Descent under criterion 7 of Requirement 4.
8. WHEN two or more Search_Workers update the visit count or the accumulated value sum of the same Book_Node or the same Book_Edge concurrently, THE Search_Coordinator SHALL apply each update as an atomic increment so that the final value equals the value obtained by applying the same updates sequentially in any order (no-lost-update invariant).
9. IF a Search_Worker terminates abnormally, THEN THE Search_Coordinator SHALL remove every Position_Key claimed by that Search_Worker from the In_Flight_Set, SHALL continue running the remaining Search_Workers, and SHALL report the Search_Worker termination to the Progress_Reporter.

### Requirement 12: Book Export for Competition Use

**User Story:** As an engine developer, I want the finished book exported in the formats my engine reads, so that the book can be used in a WCSC game.

#### Acceptance Criteria

1. WHEN the Operator invokes the export command with an Apery output path, THE Book_Exporter SHALL write an Apery_Book_File containing exactly one `BookEntry` record per exported Book_Edge, with the record's `key` field set to the Apery book key of the Book_Edge's parent Board_State, the `fromToPro` field set to the encoding of the Book_Edge's recorded move, and the `count` field set to the Book_Edge visit count clamped to the closed interval from 0 to 65,535.
2. WHEN the Book_Exporter writes an Apery_Book_File, THE Book_Exporter SHALL order the fixed-size records ascending by the `key` field value interpreted as an unsigned 64-bit integer.
3. WHEN the Book_Exporter writes two or more `BookEntry` records sharing one `key` field value, THE Book_Exporter SHALL order those records descending by the `score` field, ordering records with equal `score` descending by the `count` field and records with equal `score` and equal `count` ascending by the `fromToPro` field, so that the record order is fully determined by the record contents.
4. WHEN the Operator invokes the export command with a YaneuraOu output path, THE Book_Exporter SHALL write a YaneuraOu `.db` file through the Book_DB_Printer containing one Terashock_Entry per Book_Node that has at least one exported Book_Edge, ordered ascending by the byte-wise comparison of the SFEN string, each Terashock_Entry holding one Terashock_Move per exported Book_Edge of that Book_Node ordered descending by evaluation value.
5. IF a Book_Edge's visit count divided by its parent Book_Node visit count is below the configured Export_Visit_Threshold, THEN THE Book_Exporter SHALL exclude that Book_Edge from both the Apery_Book_File and the YaneuraOu `.db` file.
6. THE Book_Exporter SHALL set the `score` field of each exported `BookEntry` from the propagated value of the Book_Edge's child Book_Node, converted using the configured Eval_Coef, expressed from the perspective of the side to move in the parent Board_State, and clamped to the closed interval from -2,147,483,648 to 2,147,483,647.
7. FOR ALL exported Book_Edges, the move recorded in the export SHALL be a legal move of the exported position (legality invariant).
8. IF the Node_Store contains any search write applied after the completion of the most recent propagation pass, or no propagation pass has completed, THEN THE Book_Exporter SHALL report a stale-propagation warning to the Operator before writing the first record and SHALL continue the export.
9. IF a Book_Edge that would otherwise be exported has a parent Book_Node visit count of 0, or has a child Book_Node with no propagated value, or has a child Book_Node whose propagated value is stale, being a propagated value that the Value_Propagator did not compute during the most recently completed Propagation_Pass, THEN THE Book_Exporter SHALL exclude that Book_Edge from the export and SHALL count it toward the excluded-Book_Edge count reported in criterion 11.
10. IF an output path supplied to the export command cannot be opened for writing, THEN THE Book_Exporter SHALL report an error indicating the path and the reason to the Operator, SHALL leave no partial output file at that path, and SHALL leave the Book_Graph unchanged.
11. WHEN the export completes, THE Book_Exporter SHALL report the number of `BookEntry` records written, the number of Terashock_Entry records written, and the number of excluded Book_Edges to the Progress_Reporter, where the number of excluded Book_Edges is the number of Book_Edges excluded by criterion 5 together with the number of Book_Edges excluded by criterion 9.
12. WHEN the Book_Exporter writes an Apery_Book_File or a YaneuraOu `.db` file, THE Book_Exporter SHALL export the Book_Edges and the propagated best move of every Book_Node whose side to move is Black and of every Book_Node whose side to move is White, excluding a Book_Edge only where criterion 5 or criterion 9 excludes it and subject to the legality invariant of criterion 7.

WHILE a search run is in progress, THE Progress_Reporter SHALL include in the progress record required by criterion 1 the count of Book_Nodes whose expansion received at least one Terashock_Move injection and the count of Terashock_Moves discarded as illegal, both counted cumulatively from the start of the current search run.

WHERE the configured log level is verbose, WHEN a Selection_Descent produces a new Book_Node, THE Progress_Reporter SHALL record to the log destination the move sequence in USI notation from the Root_Position to that Book_Node, containing at most Max_Book_Ply moves when Max_Book_Ply is greater than zero and at most 256 moves otherwise.

6. WHILE a search run is in progress, THE Progress_Reporter SHALL include in the progress record required by criterion 1 the count of Evaluator failures reported under Requirement 5 criterion 6 and the count of duplicate Book_Node creations reported under Requirement 11 criterion 6, both counted cumulatively from the start of the current search run.

IF the Progress_Reporter cannot write a record to the log destination, THEN THE Progress_Reporter SHALL report to the Operator a failure indicating that the log destination is unwritable, SHALL discard that record, SHALL leave the search run in progress with the Book_Graph unchanged, and SHALL repeat the report at most once per Report_Interval while the log destination remains unwritable.

### Requirement 15: Search Throughput

**User Story:** As an engine developer, I want the disk-backed search to keep the GPU busy, so that a book of competition size can be built within the preparation window.

#### Acceptance Criteria

1. WHILE the Book_Graph contains at least 100,000,000 Book_Node records and Worker_Count Search_Workers run, THE Search_Coordinator SHALL complete Selection_Descents from the Root_Position such that, over a sample of at least 10,000 consecutive completed Selection_Descents taken after the first 300 seconds of the run, the elapsed time from descent start to completion of value backup is at most 1000 milliseconds at the 95th percentile and at most 10,000 milliseconds for every sampled Selection_Descent.
2. WHILE Worker_Count Search_Workers run and at least 300 seconds have elapsed since the search run started, THE Search_Coordinator SHALL sustain, in every 60-second measurement window, a rate of completed Selection_Descents per second that is at or above the configured Throughput_Floor.
3. WHILE the Book_Graph contains at least 100,000,000 Book_Node records, THE Node_Store SHALL serve a request for a Book_Node together with every Book_Edge record whose parent Position_Key equals that Position_Key such that, over a sample of at least 10,000 consecutive such requests taken after the first 300 seconds of the run, the elapsed time from request to delivery of the complete result is at most 20 milliseconds at the 95th percentile and at most 200 milliseconds at the 99th percentile.
4. WHILE a search run is in progress, THE PUCT_Book_Builder SHALL keep its resident memory, sampled at intervals of at most 10 seconds, at or below the sum of Cache_Budget, the resident memory recorded at the completion of Evaluator initialization, and 512 mebibytes of run-time overhead.
5. IF a resident memory sample exceeds the bound defined in criterion 4, THEN THE Node_Store SHALL release cached Book_Node and Book_Edge records until a subsequent sample is at or below that bound, SHALL retain every Book_Node and Book_Edge record already written to the database, and SHALL report a cache-release event to the Progress_Reporter.
6. IF a Selection_Descent does not complete within 10,000 milliseconds of its start, THEN THE Search_Coordinator SHALL abandon that Selection_Descent without applying its value backup, SHALL remove every Position_Key that the Selection_Descent added to the In_Flight_Set, and SHALL report a descent-timeout event to the Progress_Reporter (liveness guard on one Selection_Descent, not a budget on the search run defined in Requirement 4 criterion 13).
7. WHILE Worker_Count Search_Workers run and at least 300 seconds have elapsed since the search run started, THE Evaluator SHALL invoke the neural network such that the mean number of Board_States per invocation in every 60-second measurement window is at least 50 percent of the configured Batch_Size.
